# Pitfalls — deep items

The long-form half of SKILL.md's pitfalls summary: the traps whose full text (exact commands,
measured numbers, the reasoning) is too long to keep in the always-loaded body. One-line rules
1-8 stay in SKILL.md. Read this file before changing anything in these repos that touches tests,
migrations, kernels, packages, or the distro token.

9. **This user's tests must never run against the live desktop. The suite executes commands that reach systemctl/firewall/root against the INSTALLED tree (`/usr/share/omarchy`), not just the checkout** — it fires polkit/root/firewall prompts the user must deny, and the user has explicitly flagged "your testing is triggering" those prompts. When they do, drop to **static-only verification** (read files, `git diff`/`git status`, `bash -n` syntax checks) and do not execute the repo's test suites at all. When a command-family deletion breaks tests, baseline-compare a clean HEAD worktree first so you fix only YOUR regressions, not pre-existing/environmental failures. **Take that baseline without writing into `.git`:** export the committed tree (`git archive HEAD | tar -x -C <scratch>/pristine`) and re-run the SAME failing file list there (`xargs -P 8`), then compare the two sets — only a file that is green at HEAD and red with your change is yours. Expect a LARGE standing baseline rather than a clean tree: ~75 of 417 files are already red on an untouched checkout (Arch-era tests, plus tests that copy a partial tree and then reference a file the copy never included), so a failure count in that range is the normal state, not a regression. Two efficiencies: run one file directly (`bash test/shell.d/<name>-test.sh`) for the fast loop instead of the whole suite, and note that compositor-dependent files SKIP rather than fail when `WAYLAND_DISPLAY`/`HYPRLAND_INSTANCE_SIGNATURE` are unset — so invoking the suite from an agent shell leaves the live session untouched (which is exactly why this way of running it is the safe one). **And make a NEW test case fail on the OLD code before believing it:** `git show HEAD:<path> > <scratch>/old` and point the case at it — a fixture suite can pass for the wrong reason, e.g. the staged-detection fixtures all happened to carry the sibling-timestamp shapes the code handled, so the one shape the host actually produces was never exercised and the bug shipped green. **The same rule covers image-shipped desktop commands: anything that re-applies a theme or restarts a component (`omarchy-theme-set` → parallel `omarchy-restart-terminal`/btop/editor re-tints/hooks, `omarchy-restart-shell`) must never be exercised as part of testing — give such a command a `--no-theme`/`--no-reload` switch and drive it into a scratch `HOME`.** See `references/omedora-immutable-port.md` §"Verification" and §"Never run the full test/shell".
9a. **The "stubbed" L1 audits are NOT safe to run on the user's box either — they prepend the checkout's `bin/` to PATH and drive the real `omarchy-*` helpers.** `test/menu-guard-fedora-test.sh`, `test/menu-pkg-audit-test.sh` and `test/update-flow-test.sh` all look fixture-driven (stub rpm/flatpak/pacman/sudo/systemctl, temp HOME) yet still execute repo commands against the live host; running them there got "be careful with your testing you are affecting my desktop". **Run omedora's L1 tests in CI only.** To verify a test-data fix without executing it, do it statically: parse the lists yourself (the repo's own `node`/python parsers are read-only and re-usable in a scratch script), check the ids/names against the real files (`default/omarchy/omarchy-menu.jsonc`, `install/packages/fedora.toml`, `bin/`), `bash -n`, and let the CI run be the execution proof. Two traps when reading that CI job: **the L1 job aborts at the first red step**, so every later gate (`byte-identity`, the migration gates, the spec guards — including a gate you just added) shows `skipped`, not `ok`: read the per-step conclusions, never the job's conclusion alone; and **one stale row cascade turns three gates red together** — pruning a menu row means dropping it from `menu-guard-fedora-test.sh`'s `ROWS` (guardScript exits 1 on an unknown id), from `menu-pkg-audit-test.sh`'s `SAME_ON_FEDORA`/`PARTIAL_SKIPS` lists (its own stale-entry check demands it), and from any test that runs a pruned command's shim (`update-flow-test.sh` ran the deleted `bin/omarchy-snapshot`; the port's tool is `bin/omedora-snapshot` and the pipeline tolerates its absence with `|| (($? == 127))`). Standing reds not caused by a change: `test/nvim-fedora-test.sh`, and the `Upstream CLI suite (dual-distro contract)` job's `test/cli`-in-Arch-container step.
9b. **A prune cascades into the test AND CI wiring — sweep all four layers or you will chase it one red step at a time.** Deleting a command family (or a menu row) leaves: (1) `test/menu-guard-fedora-test.sh` `ROWS` ids that `guardScript()` exits 1 on; (2) `test/menu-pkg-audit-test.sh` `SAME_ON_FEDORA`/`PARTIAL_SKIPS` entries its own stale-guard demands you drop; (3) top-level `test/*-test.sh` files that run the deleted shim (`update-flow-test.sh` ran `bin/omarchy-snapshot`; the port's tool is `bin/omedora-snapshot`), copy a repo file whose sha256 must still be in the upgrader's known-default table (`upgrade-to-4-test.sh`'s retire fixture moved from `etc/fastfetch/config.jsonc` — edited by the port, so off-table — to `default/applications/mimeapps.list`), or assert the opposite of a documented prune (`hyprpad-spec-test.sh` → `build-repo.sh` says PRUNED inline); (4) `.github/workflows/test.yml` steps that `bash test/<x>.sh` a file the prune deleted (exit 127, five of them: hypxr/openclaw/basalt-xreal/xreal-ctl/monado-xreal). Sweep statically: extract every `run: bash test/*.sh` and every id/name referenced by the test files and check it against the tree. Upstream's own `test/cli` is the worst case — it asserts on specific binaries and routes (`omarchy dev benchmark cli`, the gaming installers, `hw asus` partial prefixes, `bin/omarchy-dev-theme-preview`); a missing one makes `jq -e` find no match (exit 4) or the shell report 127 and kills the suite, so re-assert each PROPERTY on a survivor instead of deleting the case (hidden commands in `--all` not in the default listing; hyphenated canonical route vs spaced filename route on `dev-env`/`theme bg-switcher`; `requires_sudo` on `omarchy-debug`) — except a partial-prefix case, which needs genuine ambiguity and must be DROPPED when no such ambiguity remains. `test/cli` is an upstream file, so those deletions need a `byte-identity` ALLOW entry.
9c. **Writing an `ALLOW` blob: escape embedded single quotes as `'"'"'`, and verify it the way the audit does.** A deleted `test/cli` line embeds `jq -e '...'`, so a plain single-quoted blob terminated early and `bash -n` failed on the very gate — a broken gate is worse than a red one, so run `bash -n` on `test/byte-identity-test.sh` before committing. Verify by SOURCING the assignment in a temp script and running the audit's line-by-line membership test over `git diff -U0 <baseline> -- <file> | grep '^-[^-]'`; do NOT extract the value with a `sed -n /start/,/^$/p` range — the blobs contain blank lines (removed blank lines are part of the diff) and the extraction silently truncates, which reads as a false MISMATCH. Baseline for the diff is the commit before your first edit to that file, since the pin tag is usually absent.
9d. **`EXCLUDED_PACKAGES` only filters the image's OWN resolved list — base-inherited and dependency-pulled packages survive it, so verify the BUILT image, never the resolver output.** Two classes, both hit here: (a) a package already in `ghcr.io/ublue-os/base-main`, where filtering the name removes only this build's copy (`google-noto-sans-cjk-fonts`, 124.6 MiB, and `qemu-user-static` — and the F44→F45 upgrade refreshes the base's NEVRA, so its install time makes it look newly added by your change); (b) a package never on that list because a BASE package `Requires` it (`google-noto-{sans,serif,sans-mono}-cjk-vf-fonts`, 116 MiB, pulled in by `default-fonts-cjk-{sans,serif,mono}`, themselves base packages). Both need a line in the removal block, and the parent metas must go WITH the children or the children are pulled straight back. **The failure is invisible to every dry run**: the resolver, `dnf5 remove --assumeno` and the cached-base simulation all agreed the CJK stack was gone while 241 MiB shipped, because all three reason about the build's list, not the base's rpmdb. Check on the box after the rebase — `rpm -qa --qf '%{NAME} %{SIZE}\n' | grep -i <family>` — or on the built image (`podman run --rm <image> rpm -q <names>`), and treat "the name is in EXCLUDED_PACKAGES" as no evidence at all. This is the same shape as the `qemu-user-static` trap; see `references/package-trimming.md` §"Verify a trim without spending a build".
9e. **A menu row whose guard is `[[ "$(omarchy-distro)" != "fedora" ]]` is VISIBLE on the immutable host — that guard predates `fedora-ostree` — so "what does clicking this do?" must be asked per row, not per row class.** 73 of 74 `install.*` rows showed on the bootc box, and 49 of them fail or install nothing when clicked (AUR refusal, "is not in the image — bake it", a skip reason, or an install that no-ops then points a default at a missing binary). The seam the fork uses is a **guard, not a refusal**: `omarchy-pkg-installable` answers whether `add` would really install (dnf/flatpak/already-baked → yes; skip, unmapped, or an unbaked dnf/copr entry on bootc → no). Three co-changes come with touching menu guards: (a) `test/menu-pkg-audit-test.sh` calls a row **gated** only when its `when` contains both `omarchy-distro` and `fedora`, so *replacing* that text with something else makes the row newly audited — keep the fedora wording (e.g. `!= fedora && != fedora-ostree`) when re-guarding an Arch-only row; (b) gating a row can make the audit's own `PARTIAL_SKIPS` keys unreachable, and its stale check then **fails the build until you drop them**; (c) the menu's `when`s are evaluated by a JS batch (`shell/plugins/menu/MenuModel.js` `fedoraPackageGuards`) that shadows the pkg predicates from ONE `pkg.py` call each — a new predicate must be added to that batch (helper chosen by host kind: the ostree helper knows what is baked, the mutable one does not) AND to `CARRIED[...]` in `test/byte-identity-test.sh`, and every changed menu line needs an `ALLOW["default/omarchy/omarchy-menu.jsonc"]` entry, single quotes escaped as `'"'"'` (pitfall 9c). Before rewriting a menu `when` that already has `||`, parenthesise the original — appending `&& X` binds to the LAST operand only, and the row stays visible. Verify the result by generating the guard batch for the rows you touched (`node` + `menu.guardScript`, per `test/menu-guard-fedora-test.sh`'s harness) and reading the `w:0/1` answers — do NOT run that suite on the live desktop (9a). Two rules that only CI surfaced: (d) **on Arch the predicate must NOT consult the Fedora map** — `superwhisper-bin` is skip-mapped there, so gating `Setup > Defaults > Dictation > Superwhisper` on installability hid the row on the one distro upstream expects to offer it (`test/voxtype-install-test.sh` asserted it shows). The wrapper now exits 0 on Arch without asking anything: a name the repos do not carry is one upstream expects from the AUR, and the row's own installer is what fails when no helper is there — the answer the menu gave before the predicate existed. (e) **an upstream test can assert a row carries NO gate at all** — the same test asserted the Voxtype row is ungated, because it is Fedora's default dictation backend and the COPR carries the RPM. Before pushing, grep the suite for `w:1`/`ungated` on every row you gate; where the gate is right, update the assertion to state the contract (yes where it can install, hidden on an immutable host that never baked it) rather than dropping the gate. Related: `EXCLUDED_PACKAGES`-style trims and gates can make an audit's own allowlists (`SAME_ON_FEDORA`, `PARTIAL_SKIPS`) unreachable — see 9b/9d.
9f. **The About's sheen refuses a coloured logo, so a branded `about.txt` animates only after TWO fixes land — the helper must read SGR runs, AND the launcher's own logo measurements must stop counting escapes (the branding notes under 12) — and the check to trust is per CELL, not per line.** Patching only the helper leaves the art still, because `build_sheen` bails the moment `measure_layout` cannot find the logo in the render. Upstream 4.5 animates the About logo with a diagonal white "sheen" (`bin/omarchy-branding-about-animation`, sourced by `omarchy-launch-about`; frames built up front, ~110 for a 54×26 logo, written at 25 ms). Its `sheen_build` requires one character = one cell and bails on ANY escape, so the fork's per-cell-coloured art (`ESC[38;2;…m` runs + `ESC[0m`) is refused (`rc=1`) and About sits still while a plain logo moves. Making it work means splitting each row into its runs and repainting only the band's cells: the run's **closing reset belongs to the run** (consume it as a boundary and the glyphs after it inherit the previous colour — the wordmark went green), a run **wholly inside the band must not emit its own colour first** (or the white never lands and everything after inherits it), and the band must be **closed the moment its right edge is reached** (or its white spills onto the art's uncoloured gaps). Keep plain rows on upstream's exact slice so plain logos stay byte-identical, and keep every refusal (wide glyphs, tabs, `$1..$9`, over-wide, empty, byte-counting locale). Verify against the real art by diffing FRAMES, not by eyeballing: per cell, glyphs must be unchanged and any cell outside the band must keep its art colour — that is what caught all three bugs above (24 957 → 116 → 0 wrong cells). A modified upstream file of this kind goes in `CARRIED[…]` in `test/byte-identity-test.sh` (rationale text, no per-line ALLOW blob), and `test/shell.d/branding-about-animation-test.sh` is upstream's own test that ASSERTS the escape refusal — extend it with a coloured-logo section instead of just flipping that case. The art itself needs no change.
9g. **The same escapes that stop the About sheen also stop the two probes that SIZE the window — so "the logo is not animated" and "the window is a bit small" are one bug, and the window half is proven through the app's own artifact.** `logo_dimensions()` runs `wc -L` over the RAW logo file, so a 54-column art measures 174; `presize_window` applies a remembered fit only when the logo measures what it measured when the fit was stored, so `~/.local/state/omarchy/windows/about.fit` (`54 26 906 554`) never matched, no size rule was applied, and the window mapped at `default/hypr/apps/system.lua`'s `920x480` — about 9 rows short of the 52-row layout, which reads as "slightly too small". `logo_landmark()` then returns the longest RAW line as the needle it searches for in fastfetch's escape-STRIPPED render, so the search can never succeed: `measure_layout` answers "the logo is not where it drew it" every time, which means `fit_window` returns before nudging or remembering (no self-correction) AND `build_sheen` returns before building a frame (no animation). Fix: one `strip_escapes` helper (`sed 's/\x1b\[[0-9;?]*[a-zA-Z]//g'`, beside `display_columns`) used by both probes. Verified on the booted image: `logo_dimensions` answers `54 x 26`, the landmark is 54 chars with no escapes and IS found in the render, and the fit file re-measured itself from the stale `54 26 906 554` to `54 26 921 573` (93 px taller than the default it had been stuck at). Read that file to prove the window half — it is written by the fixed code, not by hand. `test/shell.d/launch-about-test.sh` sources the launcher short of its launch (`sed '/^presize_window$/,$d'`) so both probes are testable without opening a window.
9h. **A predicate that asks about the FEDORA package map must not answer on Arch, and expect the L1 job to reveal menu-guard breakage one red at a time.** The guard batch's shadow for `omarchy-pkg-installable` is emitted inside the Fedora branch, but the predicate still runs as a real command on Arch, and asking Fedora's map there hid `Setup > Defaults > Dictation > Superwhisper` (skip-mapped → "not installable") on the one distro upstream shows it — `test/voxtype-install-test.sh` caught it. Arch now answers 0 without consulting anything: a name the repos do not carry is one upstream expects from the AUR, and the row's own installer is what fails without a helper. Two more shapes from the same sweep: the L1 job ABORTS at the first red, so three separate fixes each needed its own round (fix, push, watch, next red) — check what is queued behind a failing step before pushing again; and a test may assert a row carries NO gate at all (the voxtype row's "stays ungated"), which a new guard breaks — restate the contract ("shows where it can be installed") plus the immutable case that motivated the gate instead of deleting the assertion. Guard against both by sweeping for existing expectations before gating rows: `grep -rniE 'ungated|w:1|w:0' test/ | grep -iE '<row names>'`.
10. Migrations that pkg-add a not-baked package fail on bootc. Bake the package (edit `$EXCLUDED_PACKAGES` in build.sh, rebuild), don't gate the migration — **unless the package is one you deliberately do NOT want, in which case map it `source = "skip"` in `install/packages/fedora.toml`**: the same `omarchy-pkg-add` then prints the reason and exits 0 instead of killing the chain. Choose the seam by whether anything ADDS the package at runtime; grep for it (`grep -rn 'omarchy-pkg-add' migrations/ bin/ install/ | grep -w <name>`) and see `references/package-trimming.md` for the dep-tracing and the verification. Check the true baked set via `pkg.py present <name>` inside the image, warning that the map renames Arch→Fedora names. See COPR gotcha 9. **The runner DOES abort the chain on one failure — do not rely on tolerance.** Verified against the fork's `bin/omarchy-migrate`: `set -euo pipefail` at the top and a bare `OMARCHY_PATH="$OMARCHY_PATH" bash -euo pipefail "$file"` in the loop, so the first non-zero exit ends the run and every later migration stays pending (markers are touched only after a migration succeeds, so the first pending migration is the culprit). Upstream's wrapped-runner form (`if cmd; then touch marker; else warn; failed+=1; fi` — an `if`-condition never trips `set -e`) was REVERTED in #15864; a skill note claiming the runner was tolerant was wrong and cost a wrong answer to the user. Fix each offender per-migration (distro guard, or a `source = "skip"` map entry) rather than assuming one bad migration is survivable.
11. **A bootc REBASE never re-seeds `/etc/skel` into an existing user's `$HOME`.** Anything a later image adds to `/etc/skel` (e.g. `~/.config/omarchy/branding/screensaver.txt`, the HURUNAGUS ASCII-art the idle screensaver renders via `omarchy-screensaver` → `ttfx -i ~/.config/…/screensaver.txt`) reaches NEW users via `useradd -m`, but an account created BEFORE that seed was added keeps a `$HOME` without it — after rebase, whatever reads the file errors "file not found" across the screen while fresh users are fine. This is a skel-seeding gap, NOT an image defect: the file IS baked into `/etc/skel` in the image (`podman run --rm <img> ls -la /etc/skel/.config/omarchy/branding/`, read-only). Fix an existing user's missing seed with `omarchy-reinstall-configs` (copies `/etc/skel/.` → `~/`, the "adopt new defaults" path) or `cp` the one file in, then re-run. When a runtime feature breaks after a rebase with a missing-file error, check `/etc/skel` has it first — if yes, the user's `$HOME` is just stale, not the image. Document this for cross-distro rebasers in the README's Install section.
12. **The `fedora-ostree` mismatch hits COMMAND case-dispatch and `== fedora` checks too, not just migration guards (gotcha 8).** Any `case "${OMARCHY_DISTRO}" in fedora) … esac` or `[[ "$(omarchy-distro)" == fedora ]]` that is meant to cover the immutable host must match `fedora-ostree` too. This has now hit THREE commands on the fork: `omarchy-version` (fell through to Arch `pacman -Q`, `exit 1` → fastfetch OS line "unknown"), **`omarchy-version-channel`** (came only `== fedora`, so on bootc it fell to the Arch `/etc/pacman.d/mirrorlist` grep → "no such file" stderr + `unknown` → fastfetch's Software *channel/COPR* line reads "unknown"), and the migration guards. **When porting, grep the WHOLE `bin/` + configs for `case … fedora)`, `== fedora`, `in fedora` — not just `migrations/` — and add `fedora-ostree` wherever a command's FEDS execute on a bootc image** (commands that only make sense for a mutable host can keep `fedora` alone). Run `scripts/distro-dispatch-sweep.py` instead of grepping by hand, and classify each site by which failure direction it carries: a **`case … fedora) exec …/fedora/<helper>` arm STOPS MATCHING, so execution falls through to the ARCH body (pacman/yay)** — the dangerous one — while a `== "fedora"` comparison is merely FALSE, so Fedora-isms silently do not happen (the coexistence shims, the mise-work dispatch whose Arch branch would hard-fail, the lock path, the fastfetch OS line). `!= "arch"` comparisons are usually correct as they stand (they mean "runs on non-arch") — do not "fix" those. Per-site verdicts, the route-vs-refuse split for the package family, the leave-alone list and the sweep's verification: `references/omedora-upstream-sync.md` §"The dispatch sweep". `omedora-copr` itself needs no guard (it keys off `ID=fedora` in os-release, present on bootc too).
   **THE DIAGNOSTIC TRAP: `podman run --rm <img> omarchy-distro` returns `fedora`, NOT `fedora-ostree`** — a container has no `/run/ostree-booted`, so immutable-only bugs look fixed in a container probe but fail on the booted box. To reproduce an immutable path locally force it: `OMARCHY_DISTRO=fedora-ostree OMARCHY_PATH=/usr/share/omarchy <cmd>` (verify under an installed-layout path, not the git checkout, which routes to the `dev` branch). NOTE: forcing the distro still shells out to PATH-installed binaries (e.g. `omedora-copr`), so on the OLD mutable box a real silent-blow like the copr-owner default can temporarily show `agaspar/…` while the fork's own default is already `wegweg7979` — distinguish "the fork code is wrong" from "this box runs the pre-fork binary." fastfetch branding: the About OS line should read `hurunagus-hyprland — 0.2.0-beta.9` — distro name FIRST then the bare version, with the `Omedora` label AND the `(rebased on Omarchy Y)` suffix STRIPPED (the user rejected both as noise, "omedora adds some strings"). The display lives in `omedora-settings`'s `etc/fastfetch/config.jsonc` (the `"OS"` command module's `text`): it matches distro `fedora*`, sources os-release for `$NAME`, then `omarchy-version | sed 's/ (rebased.*//'` to drop the suffix. `omarchy-version` itself still prints the parenthetical (readable in `omarchy version`); strip it only in the display. A JSONC edit must stay single-level-escaped (`\\\"` not `\\\\\\\"`) — chained patch/replace operations over-escape the quotes and break the shell command; edit the line ONCE from the git baseline (checkout the file, apply one token change, re-validate by JSON-parsing after stripping `//` comments). Ships in two packages: `omarchy-version` in `omedora`, the fastfetch JSONC in `omedora-settings` — both specs must rebuild.   fastfetch's About logo comes from `etc/fastfetch/config.jsonc` `logo.source` = `~/.config/omarchy/branding/about.txt`; that file is NOT in either repo — it is shipped by `omedora-settings.spec` as `install -Dpm644 icon.txt …/etc/skel/.config/omarchy/branding/about.txt` (so `icon.txt` at the fork repo root is the source of truth). On a pre-fork box the skel copy is absent, so fastfetch auto-falls-back to its BUILT-IN Fedora spiral — that's the "green Fedora logo" if it ever shows where the omarchy O should be. To swap the logo out-of-repo for a test, write the new art to a file and point `logo.source` at it in a candidate JSONC.
   **Compositing two ASCII logos (e.g. the omarchy "O" + the Fedora spiral) and previewing them in fastfetch:** (a) get the builtin art exactly with `fastfetch --logo-type builtin --logo builtin:fedora --logo-width <w>` (module flags like `--logo-builtin` are REMOVED in v2.68 — the config `{"logo":{"type":"builtin","source":"fedora"}}` route or that flag form is the working one). (b) To overlay/nest art, build a 2D canvas in Python: place the frame glyphs (`█`) from one art as a grid, then lay the other art's non-space cells over only where the canvas is empty — doing it by string manipulation mangles the layout (the O frame is dense; a block letterfont won't fit its aperture, so a plain repeated text band reads better inside it than a tall figlet-style wordmark). (c) POINT the candidate JSONC's `logo.source` at the ABSOLUTE file path — a `sed` on `about.txt` into a tilde-relative path silently makes fastfetch fall back to auto-detect, and you'll think your comma poem failed when it's just a bad path. (d) Render with `fastfetch --config <candidate> | cat | head` — NOT piped to `awk '/Hardware/{exit}'`, because the logo's first line is the SAME line as the `┌Hardware┐` header, so that awk prints nothing/truncates and you'll conclude the logo broke when it rendered fine. (e) WITH the config's current `logo.color {"1":"green"}`, every glyph (frame `█`, text, and shaded art like `cc`/`MMM`) renders ONE flat color, so two merged marks read as a single green band — to make the wordmark distinct from the frame, map multiple color indexes (`"color": {"1":"green","2":"green",...}` palette). Note the same logo file causes fastfetch to render at DIFFERENT display widths — always eyeball the actual `head` widths, not the premise.
   **(f) Colored ASCII logos: embed per-CELL SGR, never per-whole-row SGR — and drop the config `color` block or it overrides the file.** Wrapping each LOGO LINE in one `\x1b[38;2;R;G;Bm` looks fine in the .txt but on a real terminal turns the frame's `█` bars on those rows the SPIRAL's color too (the frame looks broken/mangled mid-logo). Fix: emit a separate `\x1b[38;2;R;G;Bm` per character, keyed on char class — frame `█` one dim color, spiral glyphs (`c/M/O/d/;:,.'`) a second, wordmark letters a third — and interleave reset `\x1b[0m` after each so colors don't bleed. ALSO: any flat config `"logo":{"color":{"1":"green"}}` repaints the WHOLE logo one color and hides/per-overrides the file's embedded ANSI (all green again) — remove the `color` block to let the file's own per-cell SGR show.   Offline you can verify what colors fastfetch actually EMITS without seeing them: `fastfetch --config <cfg> 2>/dev/null | python3 -c "...Counter(re.findall(...))..."` — expect one distinct rgb per glyph class. When the probe needs real logic (multi-row iteration, f-strings, both quotes), DON'T inline it in `terminal -c "..."` — the nested quotes/braces break bash (`syntax error near unexpected token '('`). Write the check to a file (`python3 /tmp/x.py`) and pipe into `python3 /tmp/x.py` instead; it keeps the quoting clean and rerunable.
   **Char-class split pitfall: define the WORDMARK's exact letter set first, then color everything else as art — and any lowercase glyph NOT in the wordmark is a spiral/art letter, so it must take the art color.** For the `hurunagus` wordmark the only neutral letters are `h,u,r,u,n,a,g,s`; the lowercase `c,o,d,l,x,k` that ALSO appear (the bluefin spiral's `cc/mmm/odl`, etc.) are spiral glyphs, not word letters — mis-classifying them neutral leaves stray gray `dddl`/`odl` runs inside the yellow spiral. And a ONE-CHAR typo in the exempt set silently mis-colors a single word letter (writing `hurugnus` instead of `hurunagus` drops the `a`, so only the `a` renders yellow). After re-coloring, verify cheaply: count the file's per-cell SGR (`re.findall(r'\\x1b\[38;2;([\\d;]+)m')` + Counter) and spot-check one cell each class in the fastfetch emission; never trust an emitted-run count that fastfetch merges with the info column's own colors (e.g. `awk NR==11` shows frame+key+info colors interleaved — read per-cell, not per-line). 16. **A freshly built image can present as "chronologically older" to `rpm-ostree upgrade`, and the refusal has nothing to do with your content.** The guard reads `Upgrade target revision '<commit>' with timestamp '<t_target>' is chronologically older than current revision '<commit>' with timestamp '<t_current>'; use --allow-downgrade to permit`. Compare the two against the image's OWN build time: for the booted deployment `<t_current>` equals that image's `config.created` (`skopeo inspect --config docker://<image>@<digest> | jq -r .created`), and a derived image can carry its PARENT base's stamp — on this family the target's stamp equalled `ghcr.io/ublue-os/base-main:latest`'s publish time to the fraction of a second, which is how you confirm the origin before blaming your own build. The same `--check` output separates base churn from a small delta: `Added layers` / `Removed layers` near the total (264 added / 127 removed of 265, 6.3 GB here) means the new image sits on a different base, not on top of what you run. Diagnosis is read-only and needs no root — `rpm-ostree upgrade --check` and `--preview` run as the normal user (they warn they may be unreliable, and still answer "is there an update and how big is it"). The guard's own escape hatch is `--allow-downgrade`, which permits deployment of a chronologically older tree; a tree whose content is newer than the deployment is the case it exists for. Do NOT tell the user a reboot will pick up a rebuild until a deployment is actually staged.
    - **`rpm-ostree status` prints no `Staged:`/`Pending:` line when the transaction failed**, and the second deployment it lists (marked `(rollback)` by `ostree admin status`) is the PREVIOUS boot entry, not a staged update.     - **A push to the default branch builds by itself** — `gh run list -R <owner>/<repo> --limit 5` before scheduling one. 17. **Per-monitor workspaces (Omarchy 4.5+): the bar churn, the state file, and why a hand-edit vanishes.** Since 4.5 every monitor owns a **block of ten Hyprland workspace ids** — the panel 1-10, the next monitor 11-20, and so on — and each bar labels its *own* block 1-10, so the ids underneath and the labels can differ (`Super + 1` means "slot 1 of the monitor you are on"). The traps, each of which cost real time on workstation:
    - **Never pin workspaces to monitors with `hl.workspace_rule` in `~/.config/hypr`.** The pins fight the numbering: Omarchy renumbers the pinned workspaces into another monitor's block and the bar's workspace list churns (numbers appearing and disappearing). Delete the pins; 4.5 needs none. That was the real cause of "extra workspaces appearing and disappearing" here.
    - **A pre-4.5 workspaces widget is broken by the same change.** A clone that derives its list from workspace rules (e.g. `thord.workspaces`, shipped by the old hurunagus payload) falls back to "1-5 plus every open workspace" once the rules are gone — wrong per monitor, and it lists the other monitor's workspaces too.     - The assignment lives in `~/.local/state/omarchy/monitor-workspaces`, one line per monitor EVER seen: `block<TAB>connector<TAB>make-model-serial` (empty connector = unplugged). It is keyed to make/model/serial, not the connector, and the bar reads the same file for its labels.
