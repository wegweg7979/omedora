# Secure Boot support for a bootc image with a custom kernel

Load when an image must *support* firmware Secure Boot (even if the owner keeps
SB off everywhere — the usual case here), or when a signed kernel has to be
proven without touching a real host.

## What actually has to be signed — measured on this family, not assumed

On an `ublue-os/base-main`-derived image (F45, `shim-x64-16.1`, `grub2-2.12-83`):

| Link | State | Evidence |
| --- | --- | --- |
| firmware → `shimx64.efi` | fine as shipped | MS-signed (`Microsoft Windows UEFI Driver Publisher` ← `Microsoft Corporation UEFI CA 2011`), and shim embeds `.vendor_cert` = `CN=fedoraca` (`Fedora Secure Boot CA 20200709`) |
| shim → `grubx64.efi` | fine as shipped | grub is DUAL-signed: `fedora-signer-20250530` ← `fedora-ca-20250530`, **and** `kernel-signer` ← `fedoraca` — the second one is what shim's embedded cert verifies |
| grub → `vmlinuz` | **the gap** | `grubx64.efi` carries `shim_lock_verifier` + `grub_is_shim_lock_enabled` and the strings `bad shim signature` / `you need to load the kernel first`; the CachyOS `vmlinuz` had no signature table at all (PE security directory size 0) |
| modules | nothing to do | all 6552 shipped / 179 loaded modules are signed with the key generated at kernel-build time (`modinfo -F signer` → "Build time autogenerated kernel key"), which is baked into that same vmlinuz; `CONFIG_MODULE_SIG_FORCE` unset, no `extra`/`updates` tree |

BBesides how to read a PE signature table without `sbverify` (parse the MZ/PE
headers, data directory index 4 = certificate table, then `openssl pkcs7
-print_certs`), the useful commands are:
`objdump -h X.efi | grep vendor_cert`, `strings -a X.efi | grep -i shim_lock`,
and `sbverify --list X.efi` (lists every WIN_CERTIFICATE and its subject).

A signed in-image kernel reaches the bootloader unchanged: the deployed
`/boot/ostree/<csum>/vmlinuz-<kver>` is a byte-for-byte copy of
`/usr/lib/modules/<kver>/vmlinuz` (verified by sha256). dracut's initramfs does
not embed the kernel image, so signing order relative to dracut is irrelevant.

## The design shipped in hurunagus-hyprland

1. **Own key, own cert.** Fedora signs no third party and the CachyOS COPR
   publishes no `-signed` flavour (checked against live repo metadata), so the
   image signs itself — the same shape Universal Blue uses (their base kernel
   carries a self-signed `CN=ublue kernel` signature next to Fedora's).
   Generate: `openssl req -x509 -new -nodes -utf8 -sha256 -days 3650 -batch
   -config <x509.genkey> -outform PEM -out <cert>.pem -keyout <key>.key` with
   `basicConstraints=critical,CA:TRUE` + `keyUsage=critical,digitalSignature,keyCertSign`.
   RSA-4096 self-signed CA; the private half lives OUTSIDE the repo (dropped in
   `.gitignore` as well) and only in CI's `SB_SIGNING_KEY` secret.
2. **Public cert committed** at
   `system_files/usr/share/hurunagus/secureboot/hurunagus-kernel.pem`; the phase
   emits the `.der` twin at build time (`mokutil` imports DER, not PEM).
3. **Signing is its own build phase/layer** (`build.sh sign`, Containerfile
   phase 3/4) — see trap 1.
4. **Enroll helper + ujust recipe.** `/usr/bin/hurunagus-enroll-secure-boot-key`
   prompts for a MOK password (twice), runs `mokutil --timeout -1` then
   `mokutil --import <der>`, and prints the reboot order: enroll while SB is
   off → MokManager *Enroll MOK* → then enable SB in firmware. The ujust seam
   is the upstream-provided `import? "/usr/share/ublue-os/just/60-custom.just"`
   in `/usr/share/ublue-os/justfile` — ship that file; never touch the rpm-owned
   list of imports, and never reuse a recipe name (upstream already ships
   `enroll-secure-boot-key`, which enrolls *ublue's* key, password
   `universalblue`).

## Traps (each cost real time)

1. **A build secret is invisible to the layer cache, so signing must not share a
   layer with the kernel swap.** Measured: an unchanged RUN is a cache hit
   whether or not a secret is mounted, so a cached kernel layer keeps whatever it
   baked — including an *unsigned* kernel — and the phase's own assertion cannot
   help, because a cached layer is never executed. Give signing a new instruction
   (which always runs once); rotating the key then invalidates it by itself,
   because the new cert is read from the image the base layer built.
2. **Secret via `--secret`, never via `--build-arg`** — build args are recorded
   in the image config and layer history. Justfile: append
   `--secret id=sb_signing_key,src="${SB_SIGNING_KEY_FILE}"` when that var is set.
3. **`podman run --secret id=…,src=…` does NOT parse ("option id=… invalid:
   parsing secret")** — that syntax is `podman build`'s. For run-time probes bound
   the key as a file and use the phase's own `SB_SIGNING_KEY_FILE` knob.
4. **SELinux blocks bind-mounting anything under `$HOME` into a container**
   (`user_home_t` → `Permission denied`, exit 126, which looks like a broken
   script). Add `--security-opt label=disable` to test containers; do NOT reach
   for `:z` on the checkout, that relabels the user's repo files.
5. **Mounting a file *under* a directory that is also mounted** fails with
   `OCI runtime attempted to invoke a command that was not found`. Copy the file
   inside the container instead.
6. **Keep `sbsigntools` in the image.** `/usr` is read-only on a booted host, so
   `sbverify` could not be added later, and it is the only way for someone on the
   machine to check what the deployed kernel is signed with.
7. **A gate must be loud.** Default = sign and FAIL when the key is missing;
   `SB_SIGNING=off` is the explicit opt-out (CI sets it for pull requests, which
   get no secrets and are never published). A mismatch between key and committed
   cert fails in sbsign (`key values mismatch`), so the build goes red rather
   than shipping a kernel nobody trusts.

## Enrolling, per machine

Firmware only trusts keys it knows: `SecureBoot=0` + `SetupMode=0` means the PK
is enrolled, so the db route would need clearing keys in firmware setup — the
MOK route needs no firmware change and is what ublue/secureblue ship. One
enrollment per box (workstation, desktop, mini, laptop).
`mokutil --sb-state` afterwards; `mokutil --list-enrolled` should list the
hurunagus CN. Rollback from an SB-enabled state is BIOS-level: disable SB and the
old deployment (whose kernel may predate signing) boots again. That is also why
an SB-enabled fleet must not rebase onto an unsigned build — the *rollback*
entry stops booting first.

## Verifying a signed kernel without hardware: the OVMF mini-rig

Proves exactly the links that matter (firmware enforces SB → shim → grub → the
kernel's signature is accepted/refused) with no disk image, no root and no BIB:

- rig image: `dnf install qemu-kvm edk2-ovmf mtools dosfstools cpio virt-firmware`
  on `registry.fedoraproject.org/fedora:45`, run with `--device /dev/kvm`
  (`/dev/kvm` is 0666 here) and `--security-opt label=disable` (trap 4).
  **This host has no qemu and no libvirt of its own** — its only virt GUI is the
  `org.virt_manager.virt-manager` flatpak, which bundles no qemu and cannot work
  without host libvirt — so the containerised rig IS how a VM gets booted here;
  only the disk image needs the owner (`just build-qcow2` runs BIB rootful).
- `scripts/sb-rig-mk-esp.sh` builds a 400 MiB disk image with a real MBR + EFI
  System Partition holding shim (as `\EFI\BOOT\BOOTX64.EFI` and
  `\EFI\fedora\shimx64.efi`), Fedora's grub in both places shim looks, `mmx64.efi`,
  the kernel under test, the real initramfs, and a `grub.cfg` that sends the
  kernel to `console=ttyS0,115200`.
- `scripts/sb-rig-run-vm.sh` boots it (`-machine q35,smm=on` +
  `OVMF_CODE.secboot.fd` + a `virt-fw-vars`-prepared varstore), captures the
  serial console to a file, and quits via the monitor socket.
- varstores: `virt-fw-vars --input OVMF_VARS.secboot.fd --output X.fd --add-db
  d9bee56e-75dc-49d9-b4d7-b534210f637a cert.der` for the db path, and
  `--add-mok 605dab50-e046-4300-abb6-3dd810dd8b23 cert.der` for the **MOK path
  the enroll helper prepares** (MokList uses the same EFI_SIGNATURE_LIST format).
  `--print` confirms `SecureBootEnable : ON` and the var contents.

Four runs, all measured on the real image's kernel:

| Run | Expect | Got |
| --- | --- | --- |
| signed kernel + cert in db | boots | `Linux version …`, 64 dracut lines |
| **unsigned** kernel + cert in db | refused | `kern/efi/sb.c:shim_lock_verifier_write:192:bad shim signature.` + `loader/i386/efi/linux.c:grub_cmd_initrd:260:you need to load the kernel first`, 0 kernel output |
| signed kernel, cert enrolled nowhere | refused | same two errors, 0 kernel output — proves the *enrollment* authorises the kernel, not the mere presence of a signature |
| signed kernel + cert as MOK | boots | 50 dracut lines, no refusal |

Limit to state plainly: the mini-rig proves the SB links, not a full image
first-boot under SB. That needs a disk image — `just build-qcow2`, which runs
`bootc-image-builder` under **rootful** podman (`sudo`), so the owner has to run
it; then boot it in the same rig with the cert as a MOK.

## Publish-time chain (measured on the first signed release)

1. CI prints `Secure Boot signing key materialized (N characters)`. N is the
   private key file's byte count MINUS its trailing newline (3267 for a 3268-byte
   PEM), so an off-by-one there is not a wrong secret — the certificate
   fingerprint the sign phase prints is the real proof it is the right key.
2. The sign phase prints `certificate: CN=…` and `sha256 fingerprint: …`; compare
   against the committed PEM locally.
3. `podman images --digests` after `podman pull <image>:latest` must equal the
   digest the workflow's push step reported, proving the registry artifact is what
   CI built rather than a stale tag.
4. On the PULLED image: `sbverify --list /usr/lib/modules/*/vmlinuz` shows our CN,
   and `ujust --list | grep -c enroll` answers 2 (ours plus ublue's inherited one).
   On a BOOTED host the strongest form is `sbverify --cert
   /usr/share/hurunagus/secureboot/hurunagus-kernel.pem /boot/ostree/*/vmlinuz-*`
   — pass ONE file, because a glob expanding to two kernels (one per deployment)
   makes sbverify print its usage instead of verifying. Expect `Signature
   verification OK`, and the deployed copy byte-identical to
   `/usr/lib/modules/<kver>/vmlinuz` (verified: sha256 `0a0e2e27…` on the first
   signed deployment).
5. `bootc container lint` returns to its previous baseline (here 12 passed /
   2 warnings) — a pass→warning flip is how this change would show up as a
   regression, with nothing red in the log.
